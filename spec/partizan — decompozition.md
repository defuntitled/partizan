# partizan — план реализации по коммитам

Oct 23, 2026 · @kir

Каждый шаг — один коммит, после которого проект собирается, проходит CI и делает на одну вещь больше. Для каждого коммита указаны состав, DoD и тест-кейсы. Основа — спецификация partizan.

## Правила

Общий DoD действует для каждого коммита и ниже не повторяется. В разделах этапов перечислено только то, что специфично для коммита.

**Общий DoD**

- [ ] В CI зелёные `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --workspace` и `cargo deny check`.
- [ ] Все тест-кейсы коммита автоматизированы. Ручные помечены «ручной», их результат записан в описании коммита.
- [ ] Если коммит меняет поведение из спецификации, спецификация обновлена в том же коммите.
- [ ] Публичные типы и функции документированы, `TODO` без ссылки на issue не допускаются.
- [ ] Предыдущие тест-кейсы не сломаны: каждый коммит самостоятельно собирается и проходит тесты, так что работает `git bisect`.

**Соглашения**

- Формат сообщения — Conventional Commits: `feat(proto): codec for Connect frames`. В теле коммита указаны номер (`C07`) и разделы спецификации, которые он реализует.
- ID тест-кейса — `C07-T3`. Имя автотеста содержит ID: `fn c07_t3_auth_rejects_unknown_device()`. Так кейс находится по grep и в отчётах CI.
- Тип теста в таблицах: unit — внутри crate, integ — сервер и клиент в одном процессе на loopback, e2e — отдельные процессы в network namespaces, ручной — на реальном роутере или VPS.

**Все коммиты**

1. C01 — каркас workspace и CI
2. C02 — varint, адреса, `Connect` / `ConnectResult`
3. C03 — `UdpDatagram` и управляющие фреймы

5. C05 — auth: токены, заголовки, ссылка подключения, минимальный HTTP/3
6. C06 — fuzz и property-тесты для `proto`
7. C07 — `trait Transport` и QUIC на quinn
8. C08 — сервер: auth, реестр устройств, TCP dialer
9. C09 — клиент: `client-core`, SOCKS5 CONNECT, бинарь `partizan`
10. C10 — UDP NAT на сервере
11. C11 — SOCKS5 UDP ASSOCIATE на клиенте
12. C12 — кросс-сборка aarch64 и контроль размера
13. C13 — пакет OpenWrt: procd, UCI, `partizan status`
14. C14 — переподключение, rebind, `GoAway`
15. C15 — бенчмарк и настройка параметров QUIC
16. C16 — транспорт TCP+TLS с мультиплексором

## Этапы 0–1: каркас и ядро proto

Ядро `proto` пишется первым и без сети: кодеки фреймов и state machine проверяются в памяти. Это снимает риск до того, как появится транспорт.

### C01 — каркас workspace и CI

Состав: пустые crates по структуре из спецификации, `rust-toolchain.toml`, профили сборки, GitHub Actions с fmt, clippy, test, deny, `#![forbid(unsafe_code)]` в `proto` и `client-core`.

DoD: `cargo build --workspace` и весь CI проходят на чистом клоне.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C01-T1 | `cargo build --workspace` собирается с нуля | unit |
| C01-T2 | Пайплайн CI зелёный на всех шагах | unit |
| C01-T3 | `unsafe` в `proto` и `client-core` не компилируется | unit |

### C02 — varint, адреса, Connect

Состав: QUIC varint (кодер и декодер), тип `TargetAddr` (IPv4, IPv6, домен), кодеки `Connect` и `ConnectResult` с паддингом.

DoD: roundtrip кодирования стабилен, кодеки устойчивы к обрезанному и мусорному входу.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C02-T1 | varint: граничные значения 0, 63, 16383, 2^62−1 кодируются в 1/2/4/8 байт | unit |
| C02-T2 | Декод избыточно длинного varint отвергается | unit |
| C02-T3 | `Connect` со всеми типами адреса проходит roundtrip | unit |
| C02-T4 | Обрезанный `Connect` даёт `Incomplete`, а не панику | unit |
| C02-T5 | Домен длиннее 255 байт отвергается на кодировании | unit |
| C02-T6 | Паддинг декодируется и игнорируется | unit |

### C03 — UdpDatagram и управляющие фреймы

Состав: кодек `UdpDatagram` с флагом `HAS_ADDR`, управляющие фреймы `Ping`, `Pong`, `UdpClose`, `GoAway`, `Padding`, пропуск неизвестного типа ≥ 0x40 по длине.

DoD: все фреймы проходят roundtrip, неизвестные типы обрабатываются по правилам спецификации.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C03-T1 | `UdpDatagram` с `HAS_ADDR` и без него проходит roundtrip | unit |
| C03-T2 | Все управляющие фреймы проходят roundtrip | unit |
| C03-T3 | Неизвестный тип ≥ 0x40 пропускается по `length` | unit |
| C03-T4 | Неизвестный тип < 0x40 даёт `PROTOCOL_ERROR` | unit |
| C03-T5 | `GoAway` несёт код и `retry_after_ms` | unit |

### C04 — мультиплексор (sans-io)

Состав: state machine мультиплексора для TCP+TLS без сети: `OPEN`, `DATA`, `FIN`, `RST`, `WINDOW_UPDATE`, `DATAGRAM`, `CONTROL`, чётность `stream_id`, flow control, приоритет планировщика (`CONTROL` и `DATAGRAM` вперёд), дроп очереди датаграмм свыше 64 КиБ.

DoD: мультиплексор управляется шагами в тесте без tokio и сокетов, покрыты открытие, данные, закрытие, окна и приоритеты.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C04-T1 | Открытие stream, обмен данными, закрытие по `FIN` | unit |
| C04-T2 | Полузакрытие: одна сторона `FIN`, встречный поток ещё идёт | unit |
| C04-T3 | `RST` закрывает stream с кодом ошибки | unit |
| C04-T4 | Данные сверх окна не отправляются до `WINDOW_UPDATE` | unit |
| C04-T5 | `CONTROL` и `DATAGRAM` уходят раньше `DATA` того же соединения | unit |
| C04-T6 | Переполнение очереди датаграмм дропает старые, а не копит | unit |
| C04-T7 | Клиент открывает нечётные `stream_id`, сервер чётные | unit |

### C05 — auth

Состав: генерация `device_id` и токена, сборка и разбор заголовков `authorization` и `x-client`, парсер и сборщик ссылки подключения, минимальный HTTP/3-запрос (статический QPACK) и HTTP/1.1 Upgrade, state machine сессии до `AuthOk`, сравнение токена за постоянное время, `Zeroize` на секретах.

DoD: клиент и сервер сходятся на согласованных `caps` и `sid`, провал auth не отличается по времени от успеха на этапе сравнения токена.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C05-T1 | Верный токен → `AuthOk`, согласованы `caps` и `sid` | unit |
| C05-T2 | Неизвестный `device_id` и неверный токен → `AuthFailed` | unit |
| C05-T3 | Отозванное устройство → `AuthFailed` | unit |
| C05-T4 | Несовместимая версия → отказ по правилам версий | unit |
| C05-T5 | `caps` в ответе — пересечение клиента и сервера | unit |
| C05-T6 | Ссылка подключения проходит roundtrip, pin и `transport` разбираются | unit |
| C05-T7 | Сравнение токена идёт за постоянное время (статистический тест) | unit |
| C05-T8 | Секреты не попадают в `Debug` и зануляются при `drop` | unit |

### C06 — fuzz и property-тесты

Состав: `cargo-fuzz`-цели на все парсеры (`Connect`, `UdpDatagram`, управляющие фреймы, mux, auth), property-тесты roundtrip на `proptest`, лимиты длины до аллокации.

DoD: фаз-цели собираются и гоняются в CI коротким прогоном, на корпусе нет паник и OOM.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C06-T1 | Фаз-цели парсеров переживают короткий прогон CI без паник | unit |
| C06-T2 | `proptest` roundtrip на всех типах фреймов | unit |
| C06-T3 | Вход с заявленной длиной больше лимита отвергается без крупной аллокации | unit |

## Этап 2: QUIC, сервер и TCP-прокси

Первый сквозной трафик: браузер за SOCKS5 на loopback выходит в интернет через QUIC. После этого этапа проект уже полезен на десктопе.

### C07 — trait Transport и QUIC

Состав: `trait Transport` из спецификации, реализация на quinn (endpoint, открытие и приём stream, DATAGRAM, `rebind`, статистика), `rustls` с провайдером `ring`, параметры quinn из конфига, congestion control Cubic.

DoD: по QUIC между двумя эндпоинтами в одном процессе открываются stream и ходят датаграммы, флаги транспорта берутся из конфига.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C07-T1 | Эхо по bidi stream через петлю QUIC в одном процессе | integ |
| C07-T2 | Датаграмма доходит; превышающая `max_datagram_size` даёт ошибку отправки | integ |
| C07-T3 | TLS 1.3 согласован, выбран `TLS_AES_128_GCM_SHA256` | integ |
| C07-T4 | Окна и congestion control применяются из конфига | integ |
| C07-T5 | 0-RTT выключен: ранние данные не принимаются | integ |

### C08 — сервер

Состав: QUIC listener на UDP/443, проверка auth, реестр устройств из `devices.toml`, менеджер сессий, TCP dialer (резолв через hickory, Happy Eyeballs, копирование), политика egress (запрет приватных диапазонов и метаданных).

DoD: сервер принимает сессию, открывает TCP к цели и прокачивает данные в обе стороны, запрещённые цели отклоняются.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C08-T1 | `Connect` к тестовому TCP-эху, данные ходят в обе стороны | integ |
| C08-T2 | `Connect` к домену: резолв на сервере, нет резолва на клиенте | integ |
| C08-T3 | Недоступная цель → `TARGET_UNREACHABLE`, отказ по цели (0x05) → `TARGET_REFUSED` | integ |
| C08-T4 | Цель в `127.0.0.0/8`, `10.0.0.0/8`, `169.254.169.254` → `NOT_ALLOWED` | integ |
| C08-T5 | Fast open: данные после `Connect` до `ConnectResult` доходят | integ |
| C08-T6 | Полузакрытие TCP пробрасывается в обе стороны | integ |
| C08-T7 | Реестр перечитывается по SIGHUP без обрыва активных сессий | ручной |

### C09 — клиент и SOCKS5 CONNECT

Состав: `client-core` (сессия, держит соединение), SOCKS5-сервер на loopback с `CONNECT`, бинарь `partizan` с конфигом и CLI, `partizan check`.

DoD: `curl --socks5-hostname` через клиент открывает страницу в интернете, домены уходят на сервер нерезолвленными.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C09-T1 | `curl --socks5-hostname` к HTTP-серверу отдаёт верный ответ | e2e |
| C09-T2 | SOCKS5 `CONNECT` с IPv4, IPv6 и доменом | e2e |
| C09-T3 | `BIND` отклоняется с REP 0x07 | e2e |
| C09-T4 | Ошибка цели приходит в SOCKS5 верным кодом REP | e2e |
| C09-T5 | Нет DNS-резолва на стороне клиента (проверка по перехвату) | e2e |
| C09-T6 | `partizan check` проходит на валидной ссылке и внятно падает на битой | ручной |

## Этап 3: UDP

UDP делает возможными звонки и DNS. Датаграммы идут ненадёжными, full-cone NAT на сервере пускает P2P-звонки напрямую.

### C10 — UDP NAT на сервере

Состав: на каждую UDP-сессию свой dual-stack сокет, endpoint-independent mapping и filtering (full-cone), таймауты простоя (60 с, для порта 53 — 10 с), лимит UDP-сессий на устройство, `UdpClose` и `HAS_ADDR` с адресом источника в ответе.

DoD: сервер прокидывает UDP в обе стороны, ответы приходят с любого адреса (full-cone), сессии закрываются по таймауту и лимиту.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C10-T1 | UDP-эхо через сервер, ответ несёт адрес источника | integ |
| C10-T2 | Full-cone: ответ с другого адреса, чем адресат, доходит до клиента | integ |
| C10-T3 | Простой дольше таймаута закрывает сессию, порт 53 — по короткому таймауту | integ |
| C10-T4 | Сессии сверх лимита на устройство отклоняются | integ |
| C10-T5 | `UdpClose` освобождает `session_id` | integ |
| C10-T6 | Датаграмма больше `max_datagram_size` дропается и считается в `udp_oversize_drops` | integ |

### C11 — SOCKS5 UDP ASSOCIATE

Состав: `UDP ASSOCIATE` на клиенте, свой `udp_session_id` на каждый источник, привязка к управляющему TCP-соединению, дроп датаграмм с `FRAG ≠ 0`, выбор адресата по `HAS_ADDR`.

DoD: DNS и реальный звонок проходят через клиент, ICE выбирает прямой путь.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C11-T1 | DNS-запрос через `UDP ASSOCIATE` возвращает ответ | e2e |
| C11-T2 | Два источника в одной ассоциации получают разные `session_id` | e2e |
| C11-T3 | Закрытие управляющего TCP закрывает ассоциацию и её сессии | e2e |
| C11-T4 | Датаграмма с `FRAG ≠ 0` дропается | e2e |
| C11-T5 | Звонок WebRTC через клиент: `webrtc-internals` показывает прямой ICE-кандидат | ручной |
| C11-T6 | Звонок Telegram идёт без заметных артефактов | ручной |

## Этап 4: роутер

После этого этапа клиент стоит на Routerich AX3000 и обслуживает домашнюю сеть через podkop. Здесь же фиксируются цели производительности и размера.

### C12 — кросс-сборка aarch64 и размер

Состав: цель `aarch64-unknown-linux-musl`, сборка через `cargo-zigbuild`, статический бинарь, шаг CI с проверкой размера ≤ 5 МБ и отчётом `cargo bloat`.

DoD: статический клиент под aarch64 собирается в CI, размер в бюджете N5, бинарь запускается на роутере.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C12-T1 | Кросс-сборка под aarch64 musl проходит в CI | unit |
| C12-T2 | Размер stripped-бинаря ≤ 5 МБ, иначе CI падает | unit |
| C12-T3 | Бинарь запускается на роутере и печатает версию | ручной |
| C12-T4 | `ldd` подтверждает отсутствие динамических зависимостей | ручной |

### C13 — пакет OpenWrt

Состав: Makefile для OpenWrt SDK 24.10 (`mediatek/filogic`), init-скрипт procd (respawn, вывод в logd, reload-триггер), конфиг UCI, `conffiles`, admin unix-сокет и `partizan status`.

DoD: ipk ставится на роутер, демон поднимается под procd и переживает перезагрузку, `partizan status` отдаёт состояние.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C13-T1 | ipk собирается SDK и устанавливается на роутер | ручной |
| C13-T2 | Демон стартует под procd и respawn-ится после kill | ручной |
| C13-T3 | Конфиг UCI переживает перезагрузку и sysupgrade | ручной |
| C13-T4 | `partizan status` отдаёт валидный JSON состояния | ручной |
| C13-T5 | podkop с SOCKS5-outbound на клиент пускает трафик LAN-устройства в VPN | ручной |

### C14 — переподключение и rebind

Состав: экспоненциальный backoff с джиттером, прогрев сессии при старте, ожидание сессии новыми `CONNECT` до 5 с, прозрачное пересоздание UDP-сессий, `rebind` по hotplug `ifup wan`, обработка `GoAway` (`REVOKED`, `SERVER_SHUTDOWN`, `IDLE_TIMEOUT`).

DoD: клиент сам восстанавливается после рестарта сервера и смены WAN, активный звонок переживает смену адреса через connection migration.

| ID | Тест-кейс | Тип |
| --- | --- | --- |

| C14-T2 | `GoAway(REVOKED)` останавливает попытки подключения | e2e |
| C14-T3 | `GoAway(SERVER_SHUTDOWN)` даёт повтор через `retry_after_ms` | e2e |
| C14-T4 | Смена WAN-адреса: QUIC-сессия и звонок сохраняются через migration | ручной |
| C14-T5 | `CONNECT` во время переподключения ждёт до 5 с, затем REP 0x01 | e2e |

### C15 — бенчмарк и настройка QUIC

Состав: `partizan bench` и тестовый эндпоинт на сервере, прогон пропускной способности и CPU на роутере, подбор окон, MTU/PMTUD, GSO/GRO, замер добавки к RTT; фиксация цифр N2–N4 и решения по двум QUIC-соединениям.

## Этап 5: TCP+TLS и фолбэк

Запасной транспорт для сетей, где режут UDP. Мультиплексор из C04 обретает сеть.

### C16 — транспорт TCP+TLS

Состав: реализация `Transport` на `tokio-rustls` плюс мультиплексор из C04, listener TCP/443 на сервере с тем же `ServerConfig`, HTTP/1.1 Upgrade в auth, планировщик отправки (приоритет `CONTROL` и `DATAGRAM`), лимит `DATA` 16 КиБ.

DoD: весь трафик TCP и UDP ходит и по TCP+TLS, звонок работает, хоть и хуже чем по QUIC.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C16-T1 | `curl --socks5-hostname` через TCP+TLS отдаёт верный ответ | e2e |
| C16-T2 | UDP-эхо и DNS через mux-фреймы `DATAGRAM` | e2e |
| C16-T3 | Несколько TCP-потоков параллельно, данные не путаются | e2e |
| C16-T4 | Датаграмма не ждёт за большим `DATA` (приоритет планировщика) | e2e |
| C16-T5 | Переполнение очереди датаграмм дропает, задержка не растёт | e2e |
| C16-T6 | Звонок через TCP+TLS устанавливается | ручной |

### C17 — автофолбэк

Состав: режим `auto`, попытка QUIC с таймаутом 3 с, переход на TCP+TLS, запоминание выбора на 10 минут, фоновая проба QUIC, режимы `quic` и `tls` в конфиге.

## Этап 8: passthrough-маскировка

C23 реализует прозрачную L4-пересылку на настоящий сайт. Приём VPN-сессий без домена по метке REALITY (C24, только TCP+TLS) отложен; до его реализации passthrough пересылает все соединения.

### C23 — разбор ClientHello и L4-пересылка

Состав: разбор ClientHello на сервере до TLS-библиотеки, режим `passthrough` в конфиге, прозрачная пересылка TCP на `masquerade.sni:443` вместе с уже прочитанными байтами, вслепую пересылка UDP/443 на тот же сайт.

DoD: при любом ClientHello без валидной метки соединение неотличимо пересылается на чужой сайт, байты не теряются.

| ID | Тест-кейс | Тип |
| --- | --- | --- |
| C23-T1 | Обычный `curl https://server` получает контент `masquerade.sni` | e2e |
| C23-T2 | TLS-рукопожатие с чужим сайтом завершается, сертификат — настоящий сайта | e2e |
| C23-T3 | Прочитанные до решения байты доходят до апстрима без потерь | e2e |
| C23-T4 | UDP/443 вслепую уходит на `masquerade.sni` | e2e |

### C24 — метка REALITY и временный сертификат

**Статус: отложен по решению пользователя.** Патч/форк BoringSSL, хук ClientHello и зависимости только для C24 откатываются. Используется штатный `boring-sys` из crates.io. Описание и тесты ниже сохранены для будущей реализации; DoD и C24-T1–T7 не являются требованиями текущей приёмки. C22 и C23 остаются в работе независимо от C24; переход к C25 не требует завершения отложенного C24. Сейчас VPN работает в `static`, а `passthrough` обеспечивает только L4-пересылку. Подключения с pbk/sid отклоняются клиентом до сети.

Состав: статическая пара X25519, `short_id` на устройство, `auth_key = HKDF(ECDH(key_share, pbk))`, метка AES-GCM в `legacy_session_id` (версия, время, `short_id`), replay-кэш по session\_id, временный сертификат с `HMAC-SHA512` в подписи, проверка на клиенте, хук записи метки в BoringSSL, параметры `pbk` и `sid` в ссылке.

DoD: клиент с валидной меткой попадает в наш протокол и проверяет сервер по HMAC без pin, клиент без метки и зондировщик получают чужой сайт.

| C24-T2 | `short_id` отозванного устройства → пересылка на чужой сайт | e2e |
| C24-T3 | Протухшая метка (время вне ±60 с) → пересылка на чужой сайт | e2e |
