# partizan — VPN поверх QUIC/TLS, спецификация проекта

Oct 23, 2026 · @kir

## Обзор

partizan — собственный VPN из двух частей: сервер на VPS и клиент на домашнем роутере OpenWrt. Между ними работает собственный протокол поверх QUIC (основной транспорт) или TCP+TLS 1.3 (запасной). Клиент поднимает локальный SOCKS5, в который нужный трафик направляет podkop (sing-box), а сервер выходит в интернет от своего IP.

Это L4-прокси, а не L3-туннель. Через туннель идут потоки TCP и датаграммы UDP с адресом назначения, а не IP-пакеты. Это избавляет от проблем с MTU и «TCP поверх TCP».

**Цели MVP**

- Рабочий сервер на Linux (VPS) и клиент для роутера Routerich AX3000 (OpenWrt 24.10, aarch64).
- Протокол v1 с двумя транспортами и передачей TCP и UDP.
- Звонки и видео (WebRTC, Telegram, WhatsApp) работают через туннель без заметной деградации.
- На один сервер подключается много устройств, у каждого свои учётные данные.

**Не-цели MVP**

- Клиенты для Android, iOS, Windows, macOS и десктопного Linux (архитектура при этом их допускает, см. «Скоуп и roadmap»).
- TUN-режим и L3-маршрутизация на роутере: перехват остаётся за podkop.
- Собственная криптография: только TLS 1.3.
- Веб-панель, биллинг, несколько серверов с балансировкой.

**Термины**

| Термин | Значение |
| --- | --- |
| Устройство (device) | Один экземпляр клиента со своим `device_id` и токеном |
| Сессия | Аутентифицированное транспортное соединение устройства с сервером |
| Транспорт | QUIC или TCP+TLS 1.3, скрытые за общим интерфейсом |
| Stream | Двунаправленный надёжный поток, один на проксируемое TCP-соединение |
| UDP-сессия | Связка «локальный UDP-сокет клиента ↔ UDP-сокет сервера» с числовым `udp_session_id` |
| Фрейм | Единица протокола поверх транспорта |

## Требования

Четыре ключевых требования: шифрование, качество звонков и видео, скорость и много устройств на одном сервере. Из них вытекают остальные. Числа с пометкой «цель» — стартовые ориентиры, они уточняются бенчмарком на этапе 4.

**Функциональные**

| ID | Требование | Как проверяем |
| --- | --- | --- |
| F1 | TCP через SOCKS5 CONNECT (IPv4, IPv6, доменное имя) | `curl --socks5-hostname` к тестовым сайтам |
| F2 | UDP через SOCKS5 UDP ASSOCIATE | DNS-запросы, звонок WebRTC и Telegram |
| F3 | Два транспорта и автоматический фолбэк QUIC → TCP+TLS | Блокируем UDP/443 в nftables, сессия поднимается по TCP |
| F4 | Отдельные учётные данные на устройство, отзыв без перезапуска сервера | Отозванное устройство теряет сессию за ≤ 5 с |
| F5 | Резолв доменов на сервере: клиент передаёт имя, если источник трафика его отдаёт (на роутере домены резолвит podkop) | Нет DNS-утечек на dnsleaktest |
| F6 | Автопереподключение с экспоненциальной задержкой и джиттером | Рестарт сервера, обрыв WAN |
| F7 | Статус и метрики на клиенте и сервере | `partizan status`, Prometheus-эндпоинт сервера |

**Нефункциональные**

| ID | Требование | Критерий |
| --- | --- | --- |
| N1 | Шифрование | Только TLS 1.3, ECDHE (X25519), AEAD; сертификат сервера проверяется по CA или по закреплённому ключу |
| N2 | Звонки и видео | UDP идёт без перепосылок и head-of-line; цель: обработка добавляет ≤ 2 мс p50 к RTT |
| N3 | Скорость | Цель: не менее 80% пропускной способности канала до упора в CPU роутера; потолок фиксируем замером |
| N4 | Много устройств | Цель: ≥ 50 одновременных сессий на VPS с 1 vCPU и 1 ГБ RAM |
| N5 | Ресурсы клиента | Бинарь ≤ 5 МБ (stripped, static musl); RSS ≤ 32 МБ под нагрузкой |
| N6 | Устойчивость к блокировкам | Порт 443; JA4 клиента совпадает со стабильным Chrome; без валидного токена сервер отвечает как обычный HTTPS/HTTP3-сайт |
| N7 | Переносимость | Ядро протокола не зависит от ОС и рантайма, собирается под Android и iOS без изменений |

## Скоуп и roadmap платформ

В MVP входят только сервер на Linux и клиент для OpenWrt. Остальные платформы идут позже, но четыре решения принимаются сейчас, чтобы их не пришлось переписывать.

| Платформа | Этап | Как трафик попадает в клиент | Что потребуется |
| --- | --- | --- | --- |
| Сервер, Linux x86\_64 / aarch64 | MVP | — | systemd-юнит, Docker-образ |
| Клиент, OpenWrt aarch64 | MVP | SOCKS5 от podkop (sing-box) | procd-скрипт, ipk через OpenWrt SDK |
| Клиент, десктопный Linux | после MVP | SOCKS5, затем TUN | userspace TCP/IP-стек (tun2socks) |
| Клиент, Android | позже | `VpnService` (fd TUN) | обёртка UniFFI/JNI, tun2socks |
| Клиент, iOS / macOS | позже | `NEPacketTunnelProvider` | UniFFI → Swift; жёсткий лимит памяти Network Extension |
| Клиент, Windows | позже | Wintun | tun2socks, служба Windows |

**Что закладываем сейчас**

1. **Ядро протокола без I/O (sans-io).** Кодеки фреймов, state machine сессии и логика аутентификации не зависят от tokio, сокетов и часов (время передаётся снаружи). Так оно тестируется без сети и встраивается в мобильные обёртки.
2. **Источник трафика отделён от туннеля.** Клиентский движок принимает абстрактные `TcpRequest { dst, io }` и `UdpPacket { src, dst, payload }`. Сейчас их поставляет SOCKS5, позже будет TUN + tun2socks, а движок при этом не меняется.
3. **Версии и capability-флаги в handshake.** Новые возможности включаются флагом, старые клиенты продолжают работать с новым сервером.
4. **Одна ссылка подключения для всех платформ.** Сервер выдаёт на устройство URI с адресом, портами, SNI, отпечатком ключа и токеном. Роутер читает его из конфига, телефон в будущем — из QR-кода.

## Стек и архитектура

Всё написано на Rust (stable) в одном cargo workspace. Протокол лежит в одном crate, который общий для сервера и всех будущих клиентов. Слои идут снизу вверх: ядро протокола → транспорты → движок клиента или сервера → источник трафика и бинарь платформы.

**Зависимости**

| Задача | Crate | Где | Почему |
| --- | --- | --- | --- |
| QUIC | `quinn` (`quinn-proto` внутри) | клиент, сервер | Зрелый, DATAGRAM (RFC 9221), GSO/GRO, connection migration |
| TLS 1.3 | `rustls` с провайдером `ring` | сервер | На клиенте TLS делает BoringSSL (имитация Chrome). Легче `aws-lc-rs`, простая кросс-сборка, аппаратный AES на aarch64 |
| TLS поверх TCP | `tokio-rustls` | сервер | Тот же rustls; на клиенте tokio-boring |
| Async runtime | `tokio` (минимальные features) | клиент, сервер | Стандарт, нужен quinn |
| Буферы | `bytes` | везде | Zero-copy между слоями |
| Ошибки | `thiserror` | везде | Типизированные ошибки без рантайм-стоимости |
| Конфиг | `serde` + `toml` | клиент, сервер | Читаемо, цена в размере приемлема |
| CLI | `lexopt` | клиент, сервер | Десятки КБ вместо сотен у `clap` |
| Логи | `log` + свой мини-логгер (клиент), `tracing` (сервер) | — | На роутере пишем в syslog/logd |
| DNS на сервере | `hickory-resolver` | сервер | Асинхронный, с кэшем и DoH-апстримом |
| Маскировка | `hyper` (HTTPS), `h3` + `h3-quinn` (HTTP/3) | сервер | Ответ неаутентифицированным как обычный сайт |
| Метрики | `metrics` + `metrics-exporter-prometheus` | сервер | На клиенте счётчики через `status` |
| Сертификат сервера | `rustls-acme` или файлы PEM | сервер | Let's Encrypt для своего домена |
| Мобильные обёртки (позже) | `uniffi`, tun2socks на базе `smoltcp` | клиент | Одно ядро для Kotlin и Swift |

Свой мультиплексор для TCP+TLS пишем в `proto` вместо `yamux`. Так у обоих транспортов одни и те же типы фреймов, и UDP-фреймы можно приоритезировать.

**Структура workspace**

```
crates/

  transport/        # trait Transport + quic (quinn) + tls (tokio-rustls + mux из proto)
  client-core/      # движок клиента: сессия, фолбэк, реконнект, UDP-сессии
  socks5/           # источник трафика: SOCKS5 CONNECT + UDP ASSOCIATE
  server/           # bin: listenerы, auth, dialer, UDP NAT, маскировка, admin
  client-openwrt/   # bin: конфиг, CLI, сборка socks5 + client-core
  # позже: client-ffi/ (UniFFI), tun/ (источник трафика из TUN)
packaging/openwrt/  # Makefile для SDK, init.d, uci-defaults
tests/e2e/          # netns-сценарии с потерями и задержками
```

**Ключевые интерфейсы**

```rust
// transport
#[async_trait]
pub trait Transport: Send + Sync {
    async fn open_stream(&self) -> Result<(SendHalf, RecvHalf)>;
    async fn accept_stream(&self) -> Result<(SendHalf, RecvHalf)>;
    fn send_datagram(&self, data: Bytes) -> Result<(), DatagramError>; // не блокирует, при перегрузке дроп
    async fn recv_datagram(&self) -> Result<Bytes>;
    fn max_datagram_size(&self) -> Option<usize>;
    fn stats(&self) -> TransportStats;
}

// client-core: источник трафика отдаёт движку такие запросы
pub struct TcpRequest { pub dst: TargetAddr, pub io: Box<dyn AsyncReadWrite> }
pub struct UdpPacket  { pub flow: FlowKey, pub dst: TargetAddr, pub payload: Bytes }
```

**Сборка**

- Toolchain закреплён в `rust-toolchain.toml`; цели `aarch64-unknown-linux-musl` (роутер) и `x86_64-unknown-linux-musl` (сервер).
- Кросс-сборка через `cargo-zigbuild`, пакет для роутера собирается OpenWrt SDK 24.10 для `mediatek/filogic`.

## Протокол v1

Протокол передаёт TCP-потоки и UDP-датаграммы с адресом назначения поверх одного из двух транспортов. Вся криптография делегирована TLS 1.3, а аутентификация клиента оформлена как обычный HTTP-запрос. Неаутентифицированный клиент получает обычный сайт. Подход близок к Hysteria2, но формат свой.

Все целые в форматах ниже кодируются как QUIC varint (RFC 9000, §16), если не указано `u8`/`u16 BE`. Varint всегда минимальной длины: неминимальная кодировка при разборе — ошибка.

### Транспорты

|  | QUIC (основной) | TCP+TLS (запасной) |
| --- | --- | --- |
| Порт | UDP/443 | TCP/443 |
| ALPN | `h3` | `http/1.1` |
| Аутентификация | HTTP/3-запрос на первом bidi stream | HTTP/1.1-запрос с `Upgrade` |
| TCP-соединение | Отдельный QUIC bidi stream | Отдельный mux-stream |
| UDP | QUIC DATAGRAM (RFC 9221) | Mux-фрейм `DATAGRAM` |
| Head-of-line между потоками | Нет | Есть (общий TCP) |
| Смена IP клиента | Connection migration | Переподключение |

Клиент сначала пробует QUIC. Если handshake не завершился за 3 с, он переходит на TCP+TLS и запоминает это на 10 минут, после чего снова пробует QUIC в фоне. Режим задаётся в конфиге: `auto` | `quic` | `tls`.

### Handshake и аутентификация

1. **TLS 1.3.** SNI — домен сервера. Сертификат проверяется по системным CA, и дополнительно можно закрепить SHA-256 от SPKI. С pin можно работать и с self-signed сертификатом. 0-RTT выключен, session resumption (1-RTT) включён.
2. **Запрос аутентификации.** QUIC: клиент открывает первый bidi stream и отправляет HTTP/3 `POST <auth_path>`. QPACK только со статической таблицей, так что запрос собирается вручную без полного h3-клиента. TCP+TLS: `GET <auth_path> HTTP/1.1` с `Connection: Upgrade` и `Upgrade: websocket`. В обоих случаях передаются заголовки:
   - `authorization: Bearer <device_id>.<base64url(token)>`
   - `x-client: v=1; caps=<hex>; plat=openwrt; ver=<semver>`
3. **Проверка на сервере.** Ищем `device_id`, сравниваем `SHA-256(token)` с хранимым хэшем за постоянное время. Затем проверяем, что устройство не отозвано, лимит сессий не превышен, а версия поддерживается. Токен — 32 случайных байта, поэтому медленный KDF не нужен.
4. **Успех.** QUIC: ответ `200`, TCP+TLS: `101 Switching Protocols`. В ответе заголовок `x-session: v=1; caps=<hex>; sid=<hex>; udp-max=<bytes>`, где `caps` — пересечение возможностей. В QUIC этот stream дальше служит управляющим, в TCP+TLS соединение переходит в режим mux.
5. **Отказ.** Ошибку сервер не возвращает: запрос целиком уходит в маскировку (подраздел «Маскировка»). Клиент трактует любой другой статус как `AuthFailed`. Таймаут на шаги 2–4 — 10 с.

### TCP-потоки

Каждое проксируемое TCP-соединение открывается новым stream от клиента. Первые байты stream — заголовок `Connect`, дальше сырые данные в обе стороны.

```
Connect (клиент → сервер) {
  type:        varint = 0x01
  addr_type:   u8      // 0x01 IPv4, 0x03 домен, 0x04 IPv6 (коды как в SOCKS5)
  addr:        4 | 16 | (u8 len + len байт)
  port:        u16 BE
  padding_len: varint
  padding:     padding_len байт (игнорируется)
}

ConnectResult (сервер → клиент) {
  type:        varint = 0x02
  status:      u8      // 0x00 ok, остальные значения как REP в SOCKS5 (0x01–0x08)
  padding_len: varint
  padding:     padding_len байт
}
```

- **Fast open** (capability `FAST_OPEN`): клиент шлёт данные сразу после `Connect`, не дожидаясь `ConnectResult`. Это экономит один RTT на каждом соединении. Если цель недоступна, сервер возвращает ошибку и сбрасывает stream.
- **Закрытие:** FIN stream = `shutdown(Write)` на другой стороне (полузакрытие работает). RST на любой стороне = `RESET_STREAM` с кодом из таблицы ошибок.
- Адрес остаётся доменным именем, если так пришёл из SOCKS5, и резолвится на сервере (F5).
- Домен — от 1 до 255 байт в UTF-8, иначе адрес невалиден. `padding_len` не больше 1024: больший отвергается до ожидания самих байт паддинга.

### UDP

UDP идёт ненадёжными датаграммами, без перепосылок и без очереди за потерянными пакетами. Это основа качества звонков (N2).

```
UdpDatagram {
  session_id: varint      // выбирает клиент, уникален в пределах сессии
  flags:      u8          // bit0 HAS_ADDR
  [addr_type, addr, port] // если HAS_ADDR, формат как в Connect
  payload:    остаток датаграммы
}
```

- Первая датаграмма с новым `session_id` обязана иметь `HAS_ADDR`, и с неё начинается UDP-сессия. Дальше клиент ставит адрес только при смене адресата; без адреса датаграмма уходит последнему адресату.
- Остальные биты `flags` зарезервированы и должны быть 0. Невалидная датаграмма (обрезанная, с зарезервированными битами, с плохим адресом) отбрасывается и учитывается в `datagram_drops_total{reason="malformed"}`; соединение не закрывается.
- Сервер в v1 всегда ставит `HAS_ADDR` с адресом источника: он нужен SOCKS5-ответу, а в ICE-звонках отвечают разные пиры.
- Размер: если датаграмма больше `max_datagram_size` транспорта, она отбрасывается и учитывается в счётчике `udp_oversize_drops`. Фрагментации в v1 нет. В TCP+TLS ограничение — 65 507 байт.
- Закрытие: по таймауту простоя (60 с по умолчанию, настраивается) или управляющим фреймом `UdpClose`.

### Управляющий канал

В QUIC канал идёт по auth-stream, в TCP+TLS — по mux-stream 0. Формат: `type: varint, length: varint, body`. `length` не больше 16 КиБ, тело известного типа занимает ровно `length` байт, иначе `PROTOCOL_ERROR`. `u64` — 8 байт BE.

| type | Имя | Направление | Тело |
| --- | --- | --- | --- |
| 0x10 | Ping | оба | `nonce: u64` |
| 0x11 | Pong | оба | `nonce: u64` |
| 0x12 | UdpClose | оба | `session_id`, `reason: u8` |
| 0x13 | GoAway | сервер → клиент | `code`, `retry_after_ms` |
| 0x14 | Padding | оба | произвольные байты |

Типы от 0x40 и выше зарезервированы под расширения: незнакомый такой тип пропускается по `length`. Незнакомый тип ниже 0x40 — `PROTOCOL_ERROR`. Keepalive в QUIC делает сам транспорт (PING-фреймы), а Ping/Pong нужны для замера RTT и keepalive в TCP+TLS.

### Мультиплексор для TCP+TLS

```
MuxFrame {
  stream_id: varint   // нечётные открывает клиент, чётные — сервер (задел на будущее), 0 — управление
  type:      u8       // 0x0 DATA, 0x1 OPEN, 0x2 FIN, 0x3 RST, 0x4 WINDOW_UPDATE, 0x5 DATAGRAM, 0x6 CONTROL
  length:    varint
  payload:   length байт
}
```

- `OPEN` несёт `Connect`, `DATAGRAM` (всегда на stream 0) несёт `UdpDatagram`, `CONTROL` несёт фрейм управляющего канала.
- Flow control на каждый stream: начальное окно 256 КиБ, расширение через `WINDOW_UPDATE`.
- Планировщик отправки: `CONTROL` и `DATAGRAM` идут строго первыми, `DATA` — round-robin. Payload `DATA` не больше 16 КиБ, чтобы датаграмма звонка не ждала за большим фреймом.
- Очередь датаграмм ограничена 64 КиБ: сверх этого старые датаграммы отбрасываются, а не накапливают задержку.

### Коды ошибок

Коды используются как application error code в `CONNECTION_CLOSE` и `RESET_STREAM` (QUIC), в фреймах `RST` и `GoAway` (mux).

| Код | Имя | Уровень | Реакция клиента |
| --- | --- | --- | --- |
| 0x00 | NO\_ERROR | соединение, stream | — |
| 0x01 | PROTOCOL\_ERROR | соединение | Лог, переподключение |
| 0x02 | REVOKED | соединение | Стоп, без повторов |
| 0x03 | SESSION\_LIMIT | соединение | Повтор с backoff |
| 0x04 | SERVER\_SHUTDOWN | соединение | Повтор через `retry_after_ms` |
| 0x05 | IDLE\_TIMEOUT | соединение | Тихое переподключение по требованию |
| 0x10 | TARGET\_UNREACHABLE | stream | SOCKS5 REP 0x04 |
| 0x11 | TARGET\_REFUSED | stream | SOCKS5 REP 0x05 |
| 0x12 | TARGET\_TIMEOUT | stream | SOCKS5 REP 0x06 |
| 0x13 | NOT\_ALLOWED | stream | SOCKS5 REP 0x02 |

### Версии и возможности

- Версия протокола задаётся в `x-client: v=`. Сервер объявляет поддерживаемый диапазон, несовместимая версия идёт по пути отказа.
- Capability-биты v1: `0` FAST\_OPEN, `1` UDP, `2` PADDING. Дальше зарезервированы: `3` IP\_PACKETS (L3-режим для мобильных клиентов, если понадобится), `4` UDP\_FRAGMENT, `5` SERVER\_PUSH\_CONFIG.

### Имитация ClientHello Chrome

Для DPI клиент выглядит как стабильный Chrome. Шифры, расширения и их порядок, GREASE, key shares (включая гибридный X25519MLKEM768) и ALPN берутся из профиля Chrome. rustls так настроить нельзя, поэтому на клиенте TLS делает BoringSSL — тот же стек, что в самом Chrome.

- **TCP+TLS:** `boring` + `tokio-boring`. ALPN как у Chrome: `h2, http/1.1`. Сервер выбирает `http/1.1`, так что auth-запрос не меняется.
- **QUIC:** quinn с crypto-провайдером на BoringSSL. Готовый [quinn-boring](https://github.com/quinn-rs/quinn-boring) (0.1.0) написан под quinn 0.9, поэтому нужен порт на текущий quinn в своём форке. Кроме ClientHello под Chrome подгоняются transport parameters и их порядок, длина connection ID и размер первого Initial-пакета.
- **Профиль — это данные, а не код.** Он лежит в crate `transport` и обновляется вслед за релизами Chrome по захвату реального браузера. Как референс можно использовать открытые имитаторы, например [leyline-http](https://docs.rs/leyline-http): он воспроизводит TLS- и HTTP/3-фингерпринт Chrome на BoringSSL.
- **Проверка в CI:** тест сравнивает JA4 клиента с захватом Chrome (через tls.peet.ws или свой сервер, логирующий ClientHello) и падает при расхождении.
- **Цена:** BoringSSL собирается из исходников, нужны cmake и C/C++-компилятор, кросс-сборка под `aarch64-unknown-linux-musl` усложняется. Бинарь вырастет на размер BoringSSL, бюджет N5 перепроверяется на этапе 4.
- **Сервер остаётся на rustls.** Фингерпринт ответа сервера (JA4S) менее критичен, при необходимости сервер переводится на BoringSSL позже.

### Маскировка

Режим маскировки зависит от того, есть ли у сервера домен. В обоих режимах запрос без валидной аутентификации получает правдоподобный сайт, а не ошибку.

|  | `static` — с доменом | `passthrough` — без домена |
| --- | --- | --- |
| SNI клиента | Свой домен | Домен чужого сайта из `masquerade.sni` |
| Сертификат, который видит зондирующий | Let's Encrypt на свой домен | Настоящий сертификат чужого сайта |
| Как клиент проверяет сервер | CA и/или SPKI pin | HMAC-SHA512 от ключа временного сертификата, как в REALITY |
| Где решается «свой или чужой» | HTTP-запрос аутентификации после TLS | Метка в ClientHello, до ответа сервера |
| Что получает зондирующий | Статическую страницу, которую отдаёт сам сервер по HTTPS и HTTP/3 | Ответ настоящего сайта: соединение пересылается на него на уровне TCP/UDP |

В `passthrough` пересылка идёт на уровне L4, а не HTTP reverse proxy. Если сервер сам завершит TLS для чужого SNI, зондирующий увидит наш самоподписанный сертификат вместо сертификата сайта и сразу отличит сервер. Поэтому решение принимается по ClientHello, до того как сервер что-то ответил. Тот же приём использует REALITY в Xray.

**Метка в ClientHello (passthrough)**

Схема повторяет [REALITY](https://xtls.github.io/en/config/transports/reality.html) из Xray, с поправками под наш протокол.

- **Ключи.** У сервера статическая пара X25519, публичный ключ передаётся в ссылке подключения (`pbk`). У каждого устройства свой `short_id` (8 байт), он же — ключ поиска в реестре устройств. Отзыв устройства закрывает его и на уровне TLS.
- **Ключ метки.** `auth_key = HKDF-SHA256(ECDH(X25519-часть key_share клиента, pbk), salt = client_random[0..20], info = "partizan")`. Если в key\_share гибрид X25519MLKEM768 (как у Chrome), берётся его X25519-часть.
- **Метка.** `legacy_session_id` (32 байта) = `AES-256-GCM(auth_key, nonce = client_random[20..32], aad = ClientHello с обнулённым session_id)` от 16 байт открытого текста: `версия протокола (3) | резерв (1) | unix-время (4) | short_id (8)`. Получается 16 байт шифротекста и 16 байт тега, для DPI это случайные байты, как у Chrome.
- **Проверка на сервере.** Сервер разбирает ClientHello до TLS-библиотеки: тег сходится, `short_id` есть в реестре и не отозван, время в пределах ±60 с, session\_id не встречался в окне (replay-кэш — наше дополнение к REALITY). Тогда handshake ведёт сам сервер. Иначе соединение вместе с уже прочитанными байтами прозрачно пересылается на `masquerade.sni:443`.
- **Проверка сервера клиентом.** Сервер отвечает временным ed25519-сертификатом, в поле подписи которого лежит `HMAC-SHA512(auth_key, публичный ключ сертификата)`. Клиент проверяет HMAC, pin не нужен. Если пришёл настоящий сертификат чужого сайта (метку отвергли или соединение перенаправили), клиент закрывает соединение и не отправляет ничего, что отличает его от браузера.
- **После handshake** клиент отправляет тот же HTTP-запрос аутентификации, что и в `static`: он согласует версию и возможности и повторно проверяет токен.
- **QUIC в passthrough не используется**, как и в REALITY. В QUIC `legacy_session_id` всегда пуст (RFC 9001), и надёжного места для метки нет. UDP/443 сервер вслепую пересылает на `masquerade.sni`, чтобы выглядеть как обычный проброс портов. Цена: без домена работает только TCP+TLS, и звонки идут через mux с head-of-line. Для качественных звонков нужен режим `static` с доменом.
- **BoringSSL.** REALITY в Go патчит готовые байты ClientHello по смещению session\_id. В `boring` нужен хук, который даст записать метку после сборки ClientHello и до отправки. Если такого API нет, это патч в своём форке.

### Параметры QUIC (quinn)

| Параметр | Значение | Зачем |
| --- | --- | --- |
| Congestion control | Cubic (по умолчанию в quinn) | Стабильная реализация; экспериментальный BBR из quinn не используем |
| `stream_receive_window` | 4 МиБ | BDP для \~300 Мбит/с при RTT до 100 мс |
| `receive_window` / `send_window` | 16 МиБ | Несколько нагруженных потоков одновременно |
| `max_concurrent_bidi_streams` | 1024 | Браузеры и мессенджеры всего дома |
| `datagram_send_buffer_size` | 64 КиБ | При перегрузке дроп, а не задержка |
| `max_idle_timeout` / keepalive | 30 с / 10 с | Держать NAT-связки провайдера |
| MTU | старт 1200, PMTUD до 1452 | Медиапакеты WebRTC помещаются в DATAGRAM |
| UDP GSO/GRO | включены | Меньше syscall и CPU на роутере |
| 0-RTT | выключен | Риск replay |

Значения стартовые и подбираются на этапе бенчмарка. Все они вынесены в конфиг сервера и клиента.

## Сервер

Сервер — один статический бинарь на Linux. Он слушает UDP/443 и TCP/443 с одним сертификатом, аутентифицирует устройства по реестру и открывает соединения к целям от своего IP. Неаутентифицированный трафик сервер отдаёт маскировочному сайту.

### Компоненты

| Компонент | Что делает |
| --- | --- |
| Listeners | QUIC-endpoint на UDP/443 и TLS-acceptor на TCP/443, общий `rustls::ServerConfig` |
| Auth | Разбор auth-запроса, проверка токена и лимитов, выдача `x-session` |
| Реестр устройств | `devices.toml` с hot reload по SIGHUP и через admin-сокет |
| Менеджер сессий | `session_id → device`, счётчики, рассылка `GoAway` |
| TCP dialer | Резолв, Happy Eyeballs (RFC 8305), connect, двунаправленное копирование |
| UDP NAT | Свой UDP-сокет на каждую UDP-сессию, full-cone, таймауты |
| Маскировка | static: своя страница по HTTPS и HTTP/3; passthrough: разбор ClientHello и пересылка TCP/UDP на `masquerade.sni`, если в ClientHello нет валидной метки |
| Admin | Unix-сокет + подкоманды CLI того же бинаря |
| Метрики | Prometheus на `127.0.0.1:9090/metrics` |

### Управление устройствами

- `partizan-server device add <имя>` генерирует `device_id` (16 случайных байт в hex) и токен (32 байта), сохраняет только `SHA-256(token)` и один раз печатает ссылку подключения (плюс QR в терминале). Повторно токен получить нельзя, только перевыпустить через `partizan-server device rotate`.
- `partizan-server device revoke <id>`: активные сессии устройства получают `GoAway(REVOKED)` и закрываются за ≤ 5 с (F4).
- `partizan-server device list`, `partizan-server session list` показывают имя, платформу, версию, транспорт, RTT, трафик и время последнего подключения.
- Лимит одновременных сессий на устройство по умолчанию 2: при переподключении старая сессия ещё может доживать. Сверх лимита закрывается самая старая.

### Исходящие соединения

- **TCP:** резолв через `hickory-resolver` с кэшем, connect timeout 10 с, `TCP_NODELAY`, TCP keepalive, буферы копирования по 64 КиБ.
- **UDP:** на каждую UDP-сессию свой dual-stack сокет. По умолчанию endpoint-independent mapping и filtering, то есть full-cone: так P2P-звонки через ICE идут напрямую, а не через TURN. Таймаут простоя 60 с, для порта 53 — 10 с. Лимит 512 UDP-сессий на устройство.
- **Политика выхода:** по умолчанию запрещены loopback, RFC 1918, link-local, CGNAT `100.64.0.0/10` и адреса метаданных облака `169.254.169.254`. Это защита от SSRF в сеть VPS. Статус отказа — `NOT_ALLOWED`. Исключения задаются в конфиге.

### Жизненный цикл и наблюдаемость

- Graceful shutdown по SIGTERM: все сессии получают `GoAway(SERVER_SHUTDOWN, retry_after_ms)`, новые не принимаются, текущие потоки дорабатывают до 30 с.
- Метрики: `sessions_active{transport}`, `auth_total{result}`, `streams_active`, `streams_total{status}`, `udp_sessions_active`, `bytes_total{dir,transport}`, `datagram_drops_total{reason}`, `dial_duration_seconds`, `rtt_seconds`.
- Логи: токены не логируются никогда. Адреса назначения пишутся только на уровне `debug`.
- Деплой: systemd-юнит с `AmbientCapabilities=CAP_NET_BIND_SERVICE` и непривилегированным пользователем, либо Docker-образ на `scratch` с `network_mode: host`.
- Sysctl на VPS: увеличенные `net.core.rmem_max` и `wmem_max` для UDP-буферов QUIC, `net.ipv4.tcp_congestion_control=bbr` и `net.core.default_qdisc=fq` для исходящих TCP-соединений.

### Конфиг (пример)

```toml
[server]
domain     = "cdn.example.com"
listen     = "[::]:443"
auth_path  = "/api/v2/sync"
devices    = "/etc/vpn/devices.toml"
admin_sock = "/run/vpn/admin.sock"

[tls]
mode = "acme"            # домен + Let's Encrypt; "acme-ip" — сертификат LE на IP (живёт ~6 дней); "files"; "self-signed" — только с pin, для тестов
# cert = "/etc/vpn/cert.pem"
# key  = "/etc/vpn/key.pem"

[masquerade]
mode = "static"            # с доменом; "passthrough" — без домена
dir  = "/var/www/site"     # для static: страница для запросов без токена
# sni = "www.example.org"  # для passthrough: чужой сайт, куда уходят чужие соединения
# key = "/etc/vpn/x25519.key"  # для passthrough: статический ключ для меток

[limits]

udp_idle_timeout = "60s"

[egress]
deny_private = true

[quic]

receive_window = "16MiB"

[metrics]
listen = "127.0.0.1:9090"
```

## Клиент для OpenWrt

Клиент — демон под procd. Он держит одну сессию с сервером и отдаёт её через локальный SOCKS5 на `127.0.0.1:1080`, а трафик туда направляет podkop. Целевое железо — Routerich AX3000: aarch64 Cortex-A53 с AES/PMULL, \~512 МБ RAM, \~43 МБ свободно на overlay.

### SOCKS5

- Слушает только loopback, без аутентификации (`NO AUTH`). Опционально есть логин/пароль (RFC 1929), если прокси нужно открыть в LAN.
- `CONNECT`: адрес (IPv4, IPv6 или домен) уходит в `Connect` без локального резолва. Клиент отвечает успехом сразу (fast open), а ошибка цели приходит сбросом соединения. Режим «честного» ответа после `ConnectResult` включается в конфиге.
- `UDP ASSOCIATE`: на каждую ассоциацию открывается UDP-сокет на loopback, каждый источник в ней получает свой `udp_session_id`. Датаграммы с `FRAG ≠ 0` отбрасываются. Ассоциация живёт, пока открыто управляющее TCP-соединение.
- `BIND` не поддерживается (REP 0x07).

### Движок сессии

- Сессия поднимается при старте заранее, чтобы первое соединение не ждало handshake. Все потоки мультиплексируются в неё.
- Выбор транспорта и фолбэк работают по правилам из раздела «Транспорты».
- Переподключение: экспоненциальный backoff от 0,5 до 30 с с джиттером. Пока сессии нет, новые `CONNECT` ждут до 5 с, затем получают REP 0x01. TCP-потоки при потере сессии рвутся, а UDP-сессии пересоздаются прозрачно.
- Смена WAN-адреса: QUIC-endpoint делает `rebind()`, и connection migration сохраняет сессию вместе с активными звонками. Триггер — hotplug-событие `ifup wan` или ошибка отправки.
- `GoAway`: `REVOKED` останавливает попытки подключения, `SERVER_SHUTDOWN` означает повтор через `retry_after_ms`.
- Ресурсы: tokio с 2 воркерами по числу ядер, пул буферов, лимиты 1024 TCP-потока и 512 UDP-сессий. Это держит RSS в пределах N5.

### Интеграция с podkop

- В podkop выбирается тип конфигурации «Outbound» (JSON sing-box): `{"type": "socks", "server": "127.0.0.1", "server_port": 1080, "version": "5"}`. UDP sing-box передаёт через UDP ASSOCIATE.
- podkop сам резолвит домены через свой DNS, поэтому в SOCKS5 приходят IP-адреса. Защиту от DNS-утечек на роутере обеспечивает DNS podkop. Connect с доменным именем остаётся в протоколе для будущих источников трафика: TUN на телефонах и ручной SOCKS5.
- Трафик самого клиента к VPS идёт из OUTPUT роутера и не должен попадать под правила podkop. На этапе интеграции это проверяется явно, чтобы не получить петлю. IP VPS при необходимости добавляется в исключения.

### Конфигурация

Конфиг хранится в UCI (`/etc/config/partizan`), чтобы позже добавить страницу LuCI. Init-скрипт передаёт параметры бинарю. Всё про сервер задаётся одной ссылкой подключения.

```
config client 'main'
    option enabled '1'
    option uri 'partizan://<device_id>:<token_b64url>@cdn.example.com:443?path=/api/v2/sync&pin=sha256/<b64>&transport=auto'
    option socks_listen '127.0.0.1:1080'
    option log_level 'info'
```

Параметры ссылки: адрес и порт сервера, `sni` (по умолчанию хост), `path`, `pin`, `transport` (`auto` | `quic` | `tls`), `insecure` для тестов без pin и CA. В passthrough добавляется pbk (публичный ключ X25519 сервера) и sid (short\_id устройства), transport принудительно tls, а sni указывает чужой сайт.

### CLI

| Команда | Назначение |
| --- | --- |
| `partizan run --uri … --socks 127.0.0.1:1080` | Основной режим, запускается procd |
| `partizan status` | JSON через unix-сокет: состояние, транспорт, RTT, байты, потоки, UDP-сессии, дропы, переподключения |
| `partizan check --uri …` | Пробное подключение по обоим транспортам с диагностикой |
| `partizan version` | Версия бинаря и протокола |

### procd и упаковка

- Init-скрипт `USE_PROCD=1`: `procd_set_param respawn`, вывод в logd (`stdout`/`stderr`), `procd_add_reload_trigger` на свой UCI-конфиг. Старт до podkop (`START` меньше, чем у podkop).
- Пакет ipk собирается OpenWrt SDK 24.10 для `mediatek/filogic` через `rust-package.mk` из фида packages. Запасной путь — бинарь из `cargo-zigbuild`, завёрнутый в простой Makefile пакета.
- Состав пакета: `/usr/bin/partizan`, `/etc/init.d/partizan`, `/etc/config/partizan` (в `conffiles`, переживает sysupgrade), hotplug-скрипт для `ifup wan`.
- Будущие версии OpenWrt переходят на пакеты apk, поэтому Makefile пишется по стандартному шаблону фида, без ручной сборки ipk.

## Безопасность и модель угроз

Протокол защищает содержимое и адреса назначения от пассивного наблюдателя и от активного зондирования сервера. Полную неотличимость от браузерного трафика он не даёт: остающиеся риски перечислены ниже.

| Угроза | Защита | Остаточный риск |
| --- | --- | --- |
| Пассивный DPI читает трафик | TLS 1.3, всё после ClientHello зашифровано | Видны IP сервера, SNI, размеры и тайминги |
| Классификация по фингерпринту TLS | ALPN `h3` / `http/1.1`, домен с настоящим сертификатом, ClientHello Chrome на BoringSSL | Профиль Chrome нужно обновлять вслед за релизами браузера |
| Активное зондирование сервера | Без токена отвечает маскировочный сайт, нестандартный `auth_path` | Тайминги ответа; в passthrough — лишний RTT до чужого сайта через наш сервер |
| Блокировка или деградация QUIC провайдером | Автофолбэк на TCP+TLS | Звонки в TCP-режиме хуже |
| Анализ размеров и таймингов | Padding в `Connect`, `ConnectResult` и фрейм `Padding` | Статистика длинных сессий остаётся |
| Утечка токена устройства | Отдельный токен на устройство, `revoke` и `rotate`, на сервере только хэш, UCI-файл с правами 600 | До отзыва украденный токен работает |
| MITM с подменой сертификата | Проверка по CA и SPKI pin в ссылке подключения | — |
| Валидный клиент атакует сеть VPS (SSRF) | Политика выхода: запрет приватных диапазонов и метаданных | — |
| SOCKS5 доступен в LAN без пароля | По умолчанию слушает только loopback | Риск при ручной перенастройке |
| Флуд handshake и попыток auth | QUIC Retry (проверка адреса), таймаут auth 10 с, rate limit по IP на неудачные попытки | Объёмный DDoS вне скоупа |
| Уязвимости в парсерах фреймов | `#![forbid(unsafe_code)]` в `proto` и `client-core`, fuzzing парсеров, лимиты длин | — |
| Уязвимые зависимости | `cargo audit` и `cargo deny` в CI, фиксированный `Cargo.lock` | — |
| Компрометация VPS | Вне защиты протокола: сервер видит адреса назначения; логи минимальны по умолчанию | Принят |

Правила для кода: секреты хранятся в типах с `Zeroize` и без `Debug`. Токены сравниваются только за постоянное время. Любая длина из сети проверяется на верхнюю границу до аллокации.

## Этапы, тестирование и открытые вопросы

MVP собирается за семь этапов. После каждого получается рабочая версия, и уже после четвёртого туннель стоит на роутере.

### Этапы

1. **Ядро `proto`.** Varint, кодеки всех фреймов, разбор и сборка auth-запроса, state machine сессии. Unit-тесты, proptest на roundtrip, fuzz-цели.
2. **QUIC и TCP-прокси.** Транспорт на quinn, сервер с auth и TCP dialer, `client-core` и SOCKS5 `CONNECT`. Проверка локально на x86\_64.
3. **UDP.** DATAGRAM-фреймы, `UDP ASSOCIATE`, UDP NAT на сервере. Первые тестовые звонки.
4. **Роутер.** Кросс-сборка, ipk, procd, UCI, интеграция с podkop. Бенчмарк на Routerich AX3000 и подбор параметров quinn; здесь же фиксируются цели N2–N5.
5. **TCP+TLS.** Мультиплексор, планировщик с приоритетом датаграмм, автофолбэк.
6. **Эксплуатация.** Маскировка, CLI управления устройствами, `GoAway`, метрики, ACME, systemd и Docker.
7. **Укрепление.** Fuzzing в CI, `cargo audit` и `cargo deny`, e2e-сценарии с потерями и сменой адреса, неделя непрерывной работы.

### Тестирование

| Уровень | Что проверяем | Инструменты |
| --- | --- | --- |
| Unit | Кодеки, state machine, правила лимитов | `cargo test`, `proptest` |
| Fuzz | Все парсеры входных данных (фреймы, auth, SOCKS5) | `cargo-fuzz` |
| Интеграционные | Сервер и клиент в одном процессе на loopback, оба транспорта | `tokio::test` |
| E2E | Потери 1–5%, задержка и джиттер, блокировка UDP, смена IP клиента, рестарт сервера | network namespaces, `tc netem`, nftables |
| Звонки | Jitter, потери и тип ICE-кандидата (прямой или relay) | `chrome://webrtc-internals`, реальные звонки Telegram и WhatsApp |
| Производительность | Пропускная способность и CPU роутера по обоим транспортам, добавка к RTT | Встроенный `partizan bench` и тестовый эндпоинт на сервере |
| Размер | Бинарь клиента ≤ 5 МБ | CI, `cargo bloat` |

### Критерии готовности MVP

- [ ] Все устройства LAN работают через podkop и клиент 7 дней без ручного вмешательства
- [ ] Звонки Telegram, WhatsApp и Google Meet через QUIC идут без заметных артефактов, ICE выбирает прямой путь
- [ ] При заблокированном UDP сессия поднимается по TCP+TLS за ≤ 5 с
- [ ] Отозванное устройство отключается за ≤ 5 с
- [ ] Запрос без токена по HTTPS и HTTP/3 получает маскировочный сайт
- [ ] Бинарь клиента ≤ 5 МБ, RSS ≤ 32 МБ под нагрузкой
- [ ] Нет DNS-утечек при проверке через LAN-устройство

### Открытые вопросы

- Название проекта, бинарей и схемы ссылки подключения — решено (`partizan` и `partizan://`).
- Фингерпринт TLS: решено имитировать Chrome через BoringSSL (подраздел «Имитация ClientHello Chrome»). Открыто: портировать quinn-boring на текущий quinn в своём форке или ждать апстрима.
- Реализация auth в QUIC (HTTP-форма auth подтверждена, открыт только способ реализации): свой минимальный HTTP/3 (только статическая таблица QPACK) или crate `h3` с перехватом соединения после auth. От этого зависит, насколько просто отдавать чужие соединения маскировке. Рекомендация: гибрид. Сервер — crate h3 поверх своей обёртки над quinn: h3 разбирает auth-запрос и сам отдаёт static-страницу, а после успешного auth обёртка направляет новые stream соединения в наш протокол. Клиент — свой минимальный HTTP/3 (control stream с SETTINGS и GREASE как у Chrome, HEADERS со статическим QPACK).
- Congestion control: BBR в quinn не используем — решено, работаем на Cubic. На этапе 4 по бенчмарку сравниваем только Cubic и NewReno.
- Нужны ли два QUIC-соединения, чтобы нагрузить оба ядра роутера (одно QUIC-соединение в quinn обрабатывается одной задачей и упирается в одно ядро), — решается по профилированию.
- Передаёт ли podkop доменные имена в SOCKS5 outbound: нет, podkop сам резолвит домены через свой DNS, в клиент приходят IP-адреса. Вопрос закрыт.
- Маскировка: решено — два режима: static (свой домен, своя страница) и passthrough (без домена, пересылка на чужой сайт по SNI), подраздел «Маскировка». Открыто: даёт ли boring управлять legacy\_session\_id после сборки ClientHello (REALITY патчит готовые байты).
